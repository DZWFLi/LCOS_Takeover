## 最窄修复建议（本轮未施工）

修在现有 `transformR6` 和原 save-port/fetch 接缝，不另写保存器，也不全局关闭 TapNow 重试。

- **范围精确到已登记的 Core 文本 operation。** 使用现有 pending 中的 project/canvas/API/node/artifact/expectedRevision/body 身份；登记前的普通原节点、links 与无关节点沿原策略。混合批次需先按已有 operation 分组接缝隔开，不能一个 unknown 文本把其他普通节点永远卡住。
- **在 `h()` 的 catch 和下一次发送前同时查 disposition。** 首请求无可确认结果时，把该组保留在原队列的 pending 中，停止这组内层重试、25 秒 timer、cleanup flush 与显式原 retry 的写入。不要只在 catch 给 `Error` 打标签：HTTP 包装可能换 Error 身份；由准确 operation side-channel 再核对。
- **保留原状态与草稿。** 不返回假 success、不清空队列、不把 `x.current` 去重缓存当已保存、不调用 abandon/re 以隐藏红点。原 blocked owner 与离开页提醒保留；新普通操作可继续按原策略排队。
- **恢复只读。** 现有“核对保存结果”继续 GET；Core body 相同仍只算 `readback-matched-unconfirmed`，不能因此声称 spatial/history 已确认。只有精确 Core、原空间和历史回执都能核对，才按原 owner 回填并解除对应 pending；缺证据继续保留 unknown。不得调用原 `rs/retry` 自动重发未知操作。
- **冲突也需分流。** 已登记 Core 文本收到归属明确的 stale CAS 后，停止重复旧 ref；返回真实冲突与保留正文。不能把它当普通临时网络错误循环 POST。

这里只需补现有业务边界，Git/主键/CAS/普通类型不能替代客户端 unknown 处理：CAS 可挡住旧版本覆写，却不会阻止客户端重复向跨系统写入口提交同一未知操作。无需新增 hash、冻结 contract 或独立门禁。
