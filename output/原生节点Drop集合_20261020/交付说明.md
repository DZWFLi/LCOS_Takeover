# 原生节点 Drop → 集合接通与真实 GUI 验收（2026-10-20）

结论：本轮隔离实例中，图片右拖进入集合、重复投递去重、集合整体右拖成为 Composer 引用、Gallery 关开与刷新后源节点保留，全部实测通过。没有发 Run、没有调用 Provider、没有注入 Drop store。

## 两个真实断口与修复

1. 原 Pile 早已替代旧 LCOSCollectionNode 渲染器，但目标注册仍只在旧组件里，右 carry 找不到 Pile 接收口。新增 NativePileDropTarget，从 agent-ui 同 URL 导出并由原 Pile Shell 渲染，复用唯一 Drop store。使用真实节点 DOM 命中范围、已读回 Core Collection/binding 和当前 Project/Canvas/Workspace 校验。整个集合的来源引用也在这个共享模块登记，卸载只清自己持有的引用。
2. Core 成员已保存后，旧 callback 仍走 Huabu frame 几何入口，原 Pile 不同步。替换成只读 Collection projection → 原 synchronizeCollectionCarrier → 既有 lcos:native-collection-updated。失败保持 partial，不重发成员写入。
3. 接通后发现原 TapNow 的 Pile 显示会把“成员关系”当作“物理收纳”：源节点持久坐标没变，但被渲染成 pile-member-anchor 藏进卡面。现在仅对 Core Collection 引用的准确材料恢复原位置与原 parent 显示；普通原生物理 Pile 保留原行为，已展开 Group 仍由原空间 owner 负责。

## 真实 GUI

- 实例：http://127.0.0.1:56241
- runtime：isolated-node-carry-20261020
- 合成集合：collection-acba8052-1cde-40e5-8e5e-c04af92fbdc1
- Fixture 由原 Collections API 与 collections:project producer 创建。每轮只重置本脚本自己的合成集合成员。
- 图片右键按下、拖到实际集合节点、松开：Core 新增真实 artifact 成员，原卡面显示该图片，源仍原位可操作。
- 第二次从同一源节点右拖：Core 幂等返回，成员和空间节点均未复制。两次实际 POST 是两次独立用户手势；不是客户端重放。
- 点击原 Pile 打开 Gallery，确认准确成员，Esc 关闭：原源节点仍可直接命中和拖动。
- 将集合本体右拖进 Composer：仅增加一个 collection 引用，不拆成成员。
- 完整 reload：仍只有一个成员，源节点仍在原位置并具有 draggable。
- 浏览器 pageerror：0。存在原离线实验的远端 Statsig 阻断与部分 501 console 记录，不写成 console 全绿。
- 另观察到图片初始 metadata/measure 保存被现有代理拒绝（Only the exact image projection fields are accepted）；本次未修改该保存边界，也未将其掩盖为 Drop 通过。
