## 成员收口 Yellow 计划

- owner：已有 Core members HTTP producer／MutationSafety transaction + ChangeSet，原 Huabu executor 与原 lifecycle／O8 快照。没有第二成员表或历史栈。
- 文件：独占 `node-lifecycle.ts`、必要窄 membership helper 与独立测试；root owns facade 派生 DTO、原 Core 路由 source-transform/build wiring。
- 证据：真实 row 派生 `lcos_workspace_membership={workspaceId,viewId,addedAt,addedBy}`，只放原节点数据／原历史 full snapshot。它不是客户端授权，服务端每次核对当前 project／Workspace／View／binding 和 row。
- 删除：先全部准备与核对；只删除与历史证据一致的成员，随后原空间删除与 binding 读回。拒绝后来的替代成员。HTTP 返回丢失则只读真实 row；不盲重放，不假回滚。
- 恢复：只有原快照带准确成员证据时恢复同一 View 的 working-set 成员。复制新 View 不无脑继承源成员。原 carrier／binding 已建时只核对准确 ID／ref／几何，再补准确缺步；不再建第二节点，不覆盖新正文或几何。
- 并发：原 DELETE 没有 expected-row 参数，单独 preflight 不能跨 HTTP await 保住版本；需原 route 在同一同步 owner 段比较现 row，再进原 MutationSafety。此具体 race 保留到真实反例与修后验证，不新增 hash／ledger。
- partial：Core 与空间不是跨系统原子事务。任一步真实提交后下一步失败，明确保留各自事实，不能用删 binding 洗绿。

## 实际实现

- `lab/pilot/native-workspace-membership.ts` 只派生既有 row 与复用原 members HTTP producer，没有第二 store／表／队列／hash。marker 四字段必须与真实项目、Workspace、View、scope、版本及当前 row 一致。
- 删除入口沿原 `lcos_snapshots`；当前成员存在而原快照缺证据会先拒绝。准确移除成员后再调用原空间删除；后续空间不一致保留 partial，不回滚覆盖新工作。
- 恢复只在原 snapshot 带成员证据时补回同一 View；返回真实新增 row 的新 addedAt，供原历史回填。已有准确 carrier／binding 时只补缺成员，严格比位置、尺寸与正文；原 executor 的 label 去重、默认 accent 和既有 canonical 字段移除仍归原 owner，不强行重写成 GN2 样子。
- generic／文字复制沿原空间复制，只创建新 View，不自动加入 working-set；图片原 `claimImportedImageCarrier` 本来会建 member，保留该既有 policy，并在 image／copy 回执中附真实 row，而不是删除它凑统一。
- 原 Core 路由条件检查由 `native-core-workspace-membership-transform.mjs` 落在原 MutationSafety transaction callback 内。条件头为 `x-lcos-expected-workspace-member`，值是 encodeURIComponent(JSON.stringify(exactRow 或 {workspaceId,viewId,absent:true}))。未传头的原调用保持原状。新检查针对已实际复现的 HTTP await 重加 row，不是泛前置门禁。
- Core mutation 回包丢失后读取原 repository row 确认已移除／已新增，不盲发第二次；明确 HTTP 409／503 不被“目标恰好存在”伪装成成功。真实 ChangeSet 与事务保留。
