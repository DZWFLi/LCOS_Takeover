# GN2 原生图片承接续轮

状态：持续施工。图片绑定的源码路径、局部浏览器和临时 Core 持久化已验证；整个 GN2 与原用户库尚未验收。

## 结论

原生图片现在可以通过现有 Import Copy 保存字节并认领原节点，不再只在一次拖动里暂存材料身份。相同图片复用一份文件；已有 Artifact 节点不被抢占，第二只原节点使用已有的追加 View／view binding。

清除内部披露和功能承接分开验。本批没有用删除入口或遮住错误宣布完成。真实首次 Ctrl 点取、集合整体引用、非文本任务读取与用户整页联调仍有工作，继续登记施工。

## 实际代码路径

`LcosHostOverlay.prepareMaterials` → 原 `resolveNativeMaterialSources` → 原 `CoreArtifactClient.importCopiedFile` → 原 `/projects/:id/imports` → 原 `ImportCopyService` → `SqliteMetadataRepository.claimImportedImageCarrier` → 原 `ArtifactView`／`workspace_memberships`／`projection_bindings`。

认领后，`registerNativeMaterialSources` 把已确认身份交回原 `useLcosReferenceStore`；后续 `snapshotCanvasDropNodes` 直接取得正式 Artifact／View／revision 地址。仍是一份 Canvas、相机、选择与历史。

| 改动 | 实际结果 |
| --- | --- |
| 原节点认领 | 校对项目、画布、Scope、原节点、Artifact、版本和文件归属；绑定表只放身份，几何仍由 Huabu 保存 |
| 同图多处展示 | 第一次认领使用该现场的 primary View；已有材料节点时使用 `explicit_additional` View，不覆盖原绑定 |
| 事务 | View、现场成员和绑定在原 SQLite 事务中提交；字节保存仍是现有 Import Copy 阶段，不宣称跨文件／数据库全原子 |
| 重试 | 原节点已认领、字节与精确版本一致时复用原 View；不靠当前标题或新 UUID 猜历史，不新增材料 |
| 已有其它身份 | 在常见已有冲突下阻止再次导入；若其它写入者在文件提交后抢先绑定，明确报告「图片材料已保存，原节点绑定未完成」，不覆盖它 |
| 自动刷新 | 源准备结束或失败后沿原 host invalidation 和 binding refresh 读取已保存事实；成功才把身份注册到原引用 owner |
| 原图与布局 | 原图片 src、节点、位置、尺寸和选择保留；自动高度使用实际测量尺寸，没有凭默认尺寸造替代节点 |
| 原图片名字 | 真实可见名字用于导入文件的呈现名，字节不变；身份继续用原字段判断，名称不是身份 |
| 投影刷新 | 已绑定的追加 View 即使被选作当前展示，也保留独立节点与固定版本描述，避免正式身份在刷新时丢失 |
| 失败表达 | 分开显示「保存结果未确认」和「材料已保存但原图片引用未确认」，原图与输入保留 |

没有新增数据表、迁移、身份 hash、冻结 contract、baseline 或 gate。沿用原文件 hash／Import Copy 去重，不改原安全措施。

## 验证与边界

- 5 个前端测试文件，31 项通过：原生材料准备、确认到原引用 owner、下一次手势、原源保持、接收者流程、历史追加 View、尺寸和名称。
- 4 个 Core 测试文件，10 项通过，其中新图片 HTTP 测试 5 项。生产上传客户端访问测试拥有的临时 loopback Core：Main／Context 两张同图、一份字节、两个展示、精确 MIME 与内容、重复提交、关闭并重开 SQLite、已有身份冲突、文件保存后竞争以及错误现场。原用户库没有被启动、修改或迁移。
- 4 个 web-gen2 Node 测试文件，35 项通过：追加 View、原 Host facts、原 reconciliation、Presentation 读取与旧绑定修复保护。已选中的追加图片仍取得自己固定的 View／版本／文件地址。
- Web、Core、web-gen2 类型检查通过。web-gen2 的 pnpm 依赖自动处理曾要求删除 modules 目录，已停止该动作，使用现有编译器验证，没有清理或替换依赖目录。
- 浏览器使用原 Huabu `Canvas`、原 LCOS node seam、原源准备与确认函数，然后真实鼠标选择两张图片、右键整组携带到原 Composer，得到两个正式地址的 preview；Esc 恢复。登记前后仅两只原节点，原图、位置和尺寸一致，0 JavaScript 异常。
- 浏览器的第一次源准备通过原生产函数执行，Core 响应为明确隔离样例；原整页 `LcosHostOverlay` commit writer 和用户后端未挂载。真实字节／身份持久化另由上述临时 Core 验证，不能把这两类证据拼成用户整页已通过。
- 测试装配中遇到的模块被过宽 mock 路由拦截、recognizer 包装层错误、未完成原 binding read 生命周期，均已修正后重跑；没有修改产品代码去迎合这些样例错误。Vite HMR 本地网络限制仍存在，不宣称 console 全绿。

证据：`native-image-frontend-tests.json`、`native-image-core-tests.json`、`native-image-projection-tests.log`、`native-image-browser.json`、`verify-native-image-canvas.js`、`12-native-image-original-canvas.png`。

## 后续缺口

1. 第一次 Ctrl／点取引用未登记的原生图片或文本时，现有 recognizer 仍只消费已形成的正式引用；没有调用源准备。不能要求用户先拖一次才能点取。下一轮复用同一源 producer 补显式点取的桥接，保留手势阈值、当前输入和现场保护。
2. 真实 Collection 整体与 Capture／来源的 Composer／Run 引用路径。
3. 非纯文本 Run 内容读取，不能把图片已可查看等同于模型已能读取。
4. 用户完整 Core／Huabu 服务未运行；这次新参数需当前 Core 源码承接，原用户数据库与当前库也仍分开。跨服务实机、刷新、三个现场和实际模型答复继续验证。

其余窗口、阅读、助手、创建、材质和动效仍按原总清单施工，目标没有缩小。
