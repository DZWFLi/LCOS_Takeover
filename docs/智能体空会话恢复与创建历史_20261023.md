## 找到并修掉的问题

### 1. 原供应商空会话没有写出可恢复记录

绿色智能体在 0 条消息时自然断线，原进程已退出，供应商 transcript 文件不存在，原 `continue_existing` 明确报不能恢复。没有发送占位消息绕过。

隔离供应商的新会话路径现调用它自己的 `ChatRecordingService.recordSessionApprovalMode()` 和 `flush()`，保存原系统元数据，沿原写入租约、审批模式和 transcript 格式。普通模式及计划模式保留，写入拒绝／刷新失败明确失败。只修改实验副本，原安装包和备份不动。

已经丢失的这份零消息测试会话，另经受控验证使用原 ACP `session/new` 支持的指定 UUID 元数据入口，补回**同 UUID 的空会话系统元数据**。它不是找回丢失聊天内容，也不是对一般缺失历史的自动修复：工具先核对 0 条消息、原 Core 创建操作、同节点形象、旧进程退出、目标 transcript 确实不存在，才执行一次；不手写 transcript、不产生模型消息、不修改 Core。该已执行修复不可重复运行。

随后原 `session/load` 已能加载同一 native，原 Core 绑定也确认成功。

### 2. 原恢复回调实际返回恢复前的记录

真实页面发现后台恢复成功，输入框却还挂旧连接。根因是原 `recoverConversationOperation()` 成功后返回其执行前读到的 `fresh`，并不是动作完成后的新投影。接入层原先检查这份旧投影的 `core_bind`，因此提前退出。

现在只把回调作为操作身份，再通过原客户端读取同一会话、同一操作的最新状态。原连接和绑定确认、当前会话可发送后，调用原 Shell 的 `prepareComposerContinuation()`，换接当前未发送输入。草稿、Scope 引用、消息 ID 都保留；切换会话、输入已变化、发送中／结果未知、本地或 Core 有待确认消息时不替换。原错误回执继续留在原请求记录里。

### 3. 已恢复会话仍被旧失败记录反复弹卡

Core 正确保留之前的 `errorEvidence`，界面却将它永久当成当前故障。现在确认原外部会话及绑定后，这条旧连接错误不再单独触发默认恢复卡；原会话选项仍可进入全部请求、查看原操作及取消，返回后恢复正常对话。当前失败／未知／pending 步骤、未完成绑定、真实恢复动作、未确认消息和取消中状态仍会提示，功能没有删。
