这一轮不能称作全链 PASS，也不能仅归因测试等法：用户与 Agent 本来就可能连续互改。原 producer 对“有效 ACK 已确认，之后被另一方覆盖”的状态需和“没有有效 ACK 的未知提交”区分；该原 producer 的最小修复由 Canvas 分工完成，后者仍不可自动清除或重发。本人的原 state/UI 接 `NAVIGATION_MARKER_CHANGED` 的已验证 fresh facts，沿原一个 notice 表达“固定状态刚有变化，已显示最新结果。”；`verify.changed` 同理，不冒称未保存或恢复了旧状态。

另一个确切生命周期是：目录 remove 活动期间 SSE 读回把原 active attempt 映射为 pending；随后 producer 成功删掉 attempt，但用户关闭目录导致目录 refresh 被取消，旧 pending 布尔可能滞留。新增 `syncNativeNavigationPending(scene)` 仅沿准确当前 owner 回声原 attempt Map 的真实数量，在原 producer finally 调用；等值不发布，未知 Map 仍保留，不清 Map，不触镜头/回程。两个实际 state 源码专项均已新增该反例并 PASS。

脚本也补上原用户控制器完整 busy/pending/读回终态观测，供串行完整链；这不替代上面的真实并发处理。失败时保准确 UI snapshot，不靠 setter 清 pending 或 force 点击。
