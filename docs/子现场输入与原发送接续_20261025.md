## 真实断点与处理

1. 原 Composer 已打开时，默认输入停留在源现场，而提交却使用新现场的 Workspace。改为沿原 `openComposer` 切换准确输入，指定对话仍由同一接收者拥有草稿。
2. 原发送成功只更新当前输入与项目缓存，遗漏停放的新稿。现在同一成功票据结算到对应停放稿，更新消息编号，保留新文本和引用；未确认发送不提前换编号。
3. 原普通任务的局部提交状态会随输入切换清空。复用原 `referenceInputOperations` 的 sending owner，并加可选准确 inputKey；原 Assembly、Library、方法取用和画布拾取的 owner 检查保持兼容。跨项目只保留尚在发送的原 token，准备中工作和 picker 仍按原流程取消。
4. 返回同一输入会得到新的 target 对象，原对象引用相等判断导致明确错误不显示。改按原准确输入地址判断；续聊额外核对原消息／操作编号，不能把旧消息反馈放进新消息。
5. 真实子现场发送第一次被 Host 的“三根现场允许列表”拒绝。保留该列表；动态现场先验证原可逆项目／Workspace 地址，再通过同运行区固定连接调用原 Core capabilities，确认真实开放归属后挂原四工具。没有从浏览器接收命令、URL 或密钥。
6. 旧恢复测试在原能力加载完之前断言确认按钮可用。验证脚本改为等待实际能力，未放开产品按钮或伪造供应商能力。
7. 任务节点显示层把三个根现场的导航表当作全部现场的归属表，合法子现场因此被误判不可用。保留根现场 Surface 精确匹配；子现场按已确认的当前 Canvas／API、Core Workspace 和原节点事实判断，未改任务归属或放开跨现场伪造。
8. 窄屏画布重渲染产生新的 ViewerParts 包装对象，附注阅读器的 effect 因此清理正在阅读的内容，连带关闭方法来源页。改为读取最新 parts，真实卸载、项目／Canvas／API 变化仍照原规则关闭，不另建阅读器或导航状态。
9. 进入对话后，原方法详情退场却露出父方法列表，占住左下画布。现在沿同一个 reading 状态暂停父面板的可见和命中，DOM 与来源 owner 保留；返回后原面板、方法详情和焦点恢复。没有关闭重建来源，也没有另加导航状态。

Host 的动态检查仍使用原同会话并发保护、固定四项工具、原权限 Map 和原回执核对。遇到错误不输出连接配置或凭据。
