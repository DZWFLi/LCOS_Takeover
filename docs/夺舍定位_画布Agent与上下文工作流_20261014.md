# 夺舍定位：成熟画布 + LCOS 工作系统

## 结论

这次不是重新做 TapNow，也不是把我们所有旧 UI 硬塞进去。保留本地 TapNow 包里可复用的画布、节点呈现和交互，接入 LCOS 的画布 Agent、上下文、工作流与本地 Core。对用户看起来可以是一轮功能 Update；底层仍要把数据归属与运行闭环接实。

只描述本地已分析安装包，不据此判断 TapNow 最新版“绝对没有”什么能力。TapNow / TypeNow / Typebot 等口述名称，本计划统一指本地 TapNow 对象，不混用其他产品源码。

## 三层分工

| 层 | 保留 / 负责什么 |
| --- | --- |
| 成熟画布 | 原 ReactFlow、图文节点、位置/尺寸/选择、原菜单与可复用导航/历史交互；现有未通过项继续修，不等于全部可直接用。 |
| LCOS 产品增量 | Agent 作为画布对象、LCOS 已有 Work View / Composer / Review、上下文取用、Workflow 方法卡、Main / Context / Workflow 三现场；这些 LCOS 组件不是声称来自 TapNow。 |
| Local Core | 项目与材料身份、Artifact/View/Revision/FileRecord、上下文成员、方法保存、Run/Review 与产物归属。厂商云不保留为数据真值源。 |

接法是“原操作 → 小型转译适配 → 已有 Core 能力”，不是让 Core 全面冒充厂商云。界面能继续沿用的交互直接沿用；登录、计费、厂商生成及协同语义不能只换域名就当接完。

画布只保留一个实际交互 owner；Core 只保留一套领域真值。不要另挂旧画布、另建草稿 store 或重复挂 Composer。

## Agent 的真实工作闭环

用户在画布上围绕 Agent 收集图文材料 → 选择上下文/方法 → 原 Composer 明确接收者与输入 → Core Run → 执行 → Review → 接受产物 → 投影回当前工作现场。

这里 Agent 不只是一个聊天侧栏，也不只是一个头像节点。需要保留“放在哪里、用哪些材料、产物属于谁、下一步怎么发散”的联系。Workflow 方法取用不等于已经执行 DAG；创建 Run 记录也不等于模型正在工作。

## 已有证据与当前缺口

- 已测：部分原生图片/文本操作与 Core 持久化；会话对象显示、打开 Work View、拖动与刷新持久化；Saved Context 成员加入、重复处理及跨现场入口。会话内容来自手工导入历史，不是已运行 Agent 的证明。
- 本批新增：原 Workflow Hand / CardPool 接到原 Agent 入口；取用仍走已有方法读取与 Composer 草稿代码，导航仍走同一个原 Router。
- Workflow 批次实际保存一份明确标注的合成文字方法：两个动作、一条关系、引用现有 Workflow 文字材料；Core 首次保存版本 0。该批次没有生成结果或 Run。
- 后续 Run 批次已从合法会话接收者进入原 LCOS Composer，真实提交一次任务，并打开原 Review / Recipe；关闭重开与真实刷新后的同任务读取通过。任务仍为 created / planned，执行次数 0，没有产物。完整失败/恢复证据见 [原生 Run 与 Review 接入批次](原生Run与Review接入批次_20261014.md)。
- 后续人工fixture已完成原GUI Review采纳、显式投影后同节点材料与精确版本Reader的8步验收；不等于真实执行或自动刷新闭环。创建分支后的Undo/Redo仍有缺口，没有把这些未完成项算成“完整接入”。
