# 巧接 TapNow：协议翻译、三画布投影与无头空间服务

## 结论

用户提出的“像 Core 那样伪装服务器”可以落成更精准的接口兼容层：TapNow 继续使用原 Canvas/Library 请求和原节点交互，本地服务器把这些请求翻译给真实 Core 与 Huabu 空间后台。上下文/Workflow 工具走窄的选区/对象接口，不整体移植 LCOS 画布组件树。

这是对上一轮“原整包硬塞难度高”的补充方案，不是宣称完整三现场已经接通。它把工作面从整个 UI runtime 收敛到持久化协议、对象身份与少量工具挂载点。基础三画布投影有机会按中等规模验证；全量动作、撤销、跨现场和失败恢复仍是中等偏上的工程。

## 最巧的分层

```text
TapNow 原画布、节点、编辑工具与切换器
                  ↓ 原 Canvas / Library 请求
           本地协议兼容层
             ├─ Local Core：项目、材料、正文、Revision、上下文与执行
             └─ Huabu 后台：空间存储、几何、连线与命令执行

TapNow 原选区 / 当前 canvasId
                  ↓ 窄桥接 + 现有持久 binding 解析
       LCOS Context / Workflow 工具层
          （不再挂另一张 Canvas）
```

“无头”仅指不挂 Huabu 的前端 Canvas；原空间后台与命令可继续复用。TapNow 内存 store 是输入中的前端投影，不能另存一份领域/空间主数据。整个入口只保留一套活动画布和用户空间历史，不能同时驱动两套相机或两份 undo。

## 借原多画布，不新造三视图框架

现有 Core root Workspaces 已带 preferredSurface 与 canvasId。兼容层把三个真实 Workspace 投影为 TapNow Canvas 条目：Main、Context、Workflow。原切换器负责进入不同 canvasId，后端返回该现场的 nodes/connections。

不需要新增“scene”表，也不把一个 Project 粗暴当成唯一 Canvas。现有只读适配器确实是 project→canvas 目录映射，不能直接当三现场映射使用；需要改为已有 workspace/canvas 身份。子 Workspace 保持明确映射，不按名称或列表第一项猜目的地。

原“新建/复制/删除画布”只在有明确的现有 Workspace producer 和产品语义时开放；否则诚实标为未承接。删视图不默认删 Artifact，复制显示也不默认复制文件。

## 最小协议面

| 原前端请求/动作 | 本地兼容层承接 |
| --- | --- |
| GET /api/canvas/v1/canvases | 现有 Project 的 Workspace / canvasId → 原列表响应 |
| GET /api/canvas/v1/canvases/:id | Huabu 实际空间 + Core 材料/Revision → 原 nodes/connections |
| nodes:batchActions 的位置/尺寸变化 | 原 SET_NODE_GEOMETRY / 空间命令 |
| nodes:batchActions 的正文变化 | 原 Core saveCanvasText，确认后更新空间预览 |
| connections:batchActions | 原连线命令；语义关系另沿既有 Core producer |
| Library / 图片内容 | Core Artifact / FileRecord，返回真实可读字节，不回厂商云 URL |
| 打开 Context 工具 | 当前 projectId/canvasId/选区 → 持久 binding → Core entity refs |

只适配实际使用的端点，不完整仿造厂商云后台；生成、协作、订阅等未连接能力不能返回假成功或冒充权益。Core 确认保存成功才给前端成功回执。

## Context / Workflow 做工具层

已有原 Agent 侧栏替换挂载点可作为本地工具入口；也可先用显式“查看当前对象/加入上下文”操作，不要求全套跨窗口实时同步。

工具层复用已有 Core client、上下文卡面/布局和业务动作：选区解析成 entity refs 后再调用 Warehouse、Assembly apply、成员/材料读取、Run/Review 等。工具只负责自己的内容，不挂 Huabu Canvas、另一份 geometry store 或另一台相机。

ContextCollectionFace / ContextAtlasLayout 更接近 props 驱动部件；ContextAtlasStage、ContextAtlasView 和 ProfessionalWindowStage 仍有当前宿主的路由、HUD、焦点和 store 依赖，不能机械 import 后声称独立。现有 Reader/openWindow 是 LCOS 内部调用，不是原 TapNow 的通用插件 RPC。

原 store 桥已有 getSelection、getNodes、getViewport、坐标转换与更新接口；但尚无完整的 TapNow→Core binding 解析和工具持续订阅链。只读调用入口与跨窗消息都需要窄适配，不能把 iframe/postMessage 当现成能力。

## 哪些已有证据，哪些还没连

- 原 TapNow renderer/store/富文本 editor 在本地 JSON fixture 下实际跑过。本聊天主代理在北京时间 2026-10-13 14:13 的交互测试验证画布切换隔离与返回，另在 14:42 发起 8 项自动 smoke 验证编辑/保存等。切换不属于这 8 项，需分开引用；二者都不是 Core 接入证据。完整执行者、时间和原始结果见 [原 TapNow 模拟接口测试出处](./原TapNow模拟接口测试出处_20261013.md)。
- 原 Canvas ReactFlow 下已注入 LCOSOriginalNodeBridge，暴露当前 canvasId、原选区/API、undo/redo。不是恢复原 TSX，也不是完整业务桥。
- 原 Agent 侧栏已有替换模块实验，仍保留原画布，不需先重写全壳。
- 真实临时 Core HTTP 已验证正文/版本/文件；真实 Huabu 后台 storage/executor 已单独验证创建、几何、连线与重开。它们可以不依赖前端 Canvas 启动。
- 本轮实际执行现有 SurfaceRegistry 的内存探针，不加载 React/DOM/server，得到 Main/Context/Workflow 三个独立 canvas identity；domainWrites=0。这只证明端口纯逻辑能复用，不是三现场原 UI 实测。
- 尚未把“原 TapNow 多画布协议”接到“真实 Core + 无头 Huabu”，也没有完成工具层 Core 选区解析、真实跨现场流转和端到端失败恢复。

## 不能被巧接口省掉的四个问题

1. **撤销/复制身份。** 原 TapNow 删除后撤销会生成新 node ID。必须保留材料/View 身份，并有明确动作意图或绑定重映射；不能从 create 批次随意猜“撤销还是新材料”。
2. **版本冲突。** 原 wire 未证明会携带 Core 的 expectedRevision。可能需要小型前端 shim 带上读到的 revision/现有幂等参数，不能在服务器偷偷拿最新版本覆盖并发修改。
3. **两段写入失败。** Core 正文与空间几何分别归原 owner；一边成功一边失败必须明确显示和可重试，不能 fake 200，也不为了兼容删除原事务/CAS。
4. **内容与空间语义。** 正文实际读 data.text，旧 content 可能陈旧；跨现场引用、移动、视图复制、Artifact 删除和 Core Relation 是不同动作。接口外观相同不代表业务语义相同。

## 生产边界与下一条实验

当前正式 GN2 仍规定 Huabu 为唯一前端 Canvas kernel。本方案是独立工作区中的备选实验：若未来选择 TapNow 为唯一画布前端，要明确替换现有前端边界，保留或明确调整空间后台，不能把两套前端并排当成完整采用。本轮未修改任何生产约束。

最有价值的下一条纵切：一个新合成 Project 的三个真实 root Workspace，以原 TapNow 列表/切换器读取真实空间；先验证一张本地图片、一个文本、拖动/编辑/刷新，再加一个 Context 工具动作。按这个小范围验证，不先复制完整营销、账户、计费和云任务体系。

本轮只做源码核对、纯逻辑探针与文档归档，没有实施该桥接、启动新服务、读旧用户 DB、改原件或提交模型任务。LCOS 后端技能让方案保留原 Core/空间 owner 和诚实回执；没有新增 hash、冻结 contract、baseline 或 gate。
