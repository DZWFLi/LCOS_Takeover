**Codex：**

```text
**我们的方案像改造一座已经能正常运转的剧院：保留舞台机械，重新设计布景、道具和演员的动作，再把后台接上。** Huabu 就是这座剧院，我们不是拆掉它重盖。

你可以分成五层理解：

**① Huabu 保留“舞台机械”**

画布拖动、缩放，节点移动、选中、调整大小，以及空间操作的撤销，这些继续交给 Huabu。

因为这些功能彼此牵连很深。自己再写一套相机或拖拽，看起来只是多几个函数，最后却可能出现“鼠标认为节点在这里，画面认为它在那里”。所以我们尽量保留它已经工作的底层。

**② 给原有节点换“外观和内部陈设”**

普通节点、Glyth、上下文集合、工作流集合，外观和内部操作各不相同，但可以继续使用 Huabu 的节点底座。

像同一种建筑结构，可以装修成书店、展厅或工作室。**房子的承重结构不换，门面、内容和用途变了。**

这就是我们说的 *body 接口*：Huabu 负责“这个节点在哪里、怎么移动”，LCOS 决定“里面显示什么、用户可以做什么”。上下文体块落到 Main 后，可以呈现平面或伪 2.5D，也不需要另造一个画布。

**③ 用“身份证对照表”把画面接到真实业务**

画布上的 Glyth 是一个视觉节点，Core 里则有它对应的真实会话。

两者之间有一张对照表，叫 `ProjectionBinding`。你可以理解为：

> 舞台上这个道具，代表后台档案里的哪个对象？

所以把同一集合放到不同现场，不必复制它的全部内容；不同位置可以展示同一个对象。删掉其中一个展示，也不应该把原资料删了。

**④ Portal、工作流手牌和专业窗口，尽量接现成装置**

Portal 已经有预览另一个空间、进入目标等能力，我们就复用它，让上下文子画布、工作流现场接入同一条通道。

工作流手牌则像随时能拿出的工具牌盒。你在 Main 呼出它、选卡、交给 Glyth，**不需要把牌盒变成另一个画布，也不需要先把每张牌放成节点。**

Assembly、Work View 等窗口共用一套窗口管理，统一安排位置、遮挡和焦点，避免每个功能自己造一扇门、自己抢屏幕。

**⑤ 按钮是“前台点单”，Core 和 Adapter 才负责干活**

完整链路是：

`​``text
你点击或拖放
→ 前端说明“你要对哪个对象做什么”
→ Core 检查并处理业务
→ 需要外部 Agent 时，由 Adapter 调用
→ 返回真实结果
→ 前端更新画面
`​``

像餐厅：菜单漂亮、服务员记下订单，都不代表菜做好了。**必须厨房真正处理，前台收到结果，才能告诉你完成。**

这也是刚才 WaitingInput／Recovery 暴露的问题：有些“菜单和接单窗口”做好了，但后面的处理链还没全部接通。纠偏就是要求从真实入口一直测到结果，而不是只检查按钮能显示。

你关心的“以后改一个东西，能不能只动一点”，主要就靠这些边界：

- 改集合造型，主要动对应的外观组件。
- 改窗口布局，主要动窗口容器。
- 改会话处理规则，主要动 Core。
- 换一个 Agent，主要动 Adapter。
- 画布拖动缩放，继续用 Huabu。

**模块化不等于文件越多越好，而是每件事只有一个明确负责人。** 有些改动仍需两三层一起配合，但不应该为了换一张工作流卡的样子，就重写整座“剧院”。
```

**Codex：**

```text
**原来就有，而且我们采用的 Huabu 版本里已经包含它。** 最近新增的是“用连线限制指令给哪些 Agent”，不是第一次出现 Prompt Frame。我前面没强调清楚。

它像画布里的**“入职说明框”**：

- 一个 Frame 被明确命名为 `Prompt` 或 `Prompt: …` 时，会被识别为指令框。
- 系统读取框内直接包含的文字、笔记，整理成一段指令。
- 普通集合、普通节点不会因为摆在画布上就自动变成 Prompt。

**不是每新建一个节点，就把它发给挂靠的 Agent。** 触发逻辑是：

| 操作 | 会发生什么 |
|---|---|
| 只创建 Agent 节点 | 不采集、不启动 |
| 第一次发消息 | 采集当时适用的 Prompt，写入该 Agent 的工作配置 |
| 创建并立即开始 | 创建完成后随首次消息采集 |
| 后来修改 Prompt 或连线 | 不自动替换已建立的工作配置 |
| 外接 Agent 首次修改模型／模式等控制项 | 也可能提前触发配置建立 |

所以更像**开始工作时领一份说明书**，不是画布上有变化就不断给它发消息。[上游生命周期说明](https://github.com/microsoft/Huabu/blob/main/docs/proposals/space-prompt-topology-scoping.md)

还有一个与你担心直接相关的区别：

- **我们采用的旧版本**：Prompt Frame 是整个 Space 的公共指令。
- **最新版本**：没连 Agent 仍是公共指令；直接连了哪些 Agent，就只给那些 Agent。

**它确实可能干扰 LCOS，但不是必然冲突。** 如果 LCOS 已经准备好材料和指令，Huabu 又额外加入公共 Prompt，就可能出现重复内容，甚至两份要求互相矛盾。尤其“没连线仍全局生效”容易让用户没意识到。

融合时应该做到：**最终发给 Agent 的内容有一个明确汇总点，能解释每段指令来自哪里。** 原生 Prompt Frame 可以保留为指令来源，但不能成为 LCOS 看不见的第二条注入通道。至于我们现有调用链是否已经触发它，还需要单独核接线，不能仅凭它存在就断言已经干扰。
```
