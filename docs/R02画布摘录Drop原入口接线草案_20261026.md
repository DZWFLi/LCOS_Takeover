## placement / receive 能用什么

| 现 owner | 能复用 | 不能冒充 |

| [material projection 同步](<E:/Codex 项目/LCOS夺舍计划_20261013/lab/startup-node-bridge.js:251>) | canonical 结果已保存时，将真实 carrier 回填给同一原 Canvas/O8，并等实际发布，避免第二次 addNodes / 相机变化 | [现 material-projection 分支](<E:/Codex 项目/LCOS夺舍计划_20261013/lab/startup-history-intent.js:2190>)走全历史 canonical 回填；仅调 placement 看到节点，不能据此宣称“本次新建摘录可 Undo/Redo” |

因此首刀推荐直接复用下节原创建链，placement/receive 保留各自现用途。后续若某个“已有摘录再次投放”入口使用 placement，应当进入已有派生 Artifact 的确版地址，不能再跑文本 producer。

## 最小完整施工顺序

1. **原 c7 认领手势。** 只认结构化 text material MIME，真实画布空白且未被 modal、节点、原 chrome、输入/资料库遮挡才投放；保原语义 Drop 正在 tracking/committing 时的优先权，不把它改成 Assembly payload。拖入反馈借原 c7 遮罩，不新开 HUD。释放时一次捕获 project、canvas、Workspace、API、准确来源和 `screenToFlowPosition(clientPoint)`，异步后不改落点、不选别的现场。
2. **沿原普通 text create。** 同页 `_E` 已用 `$e().addNodes` 与 `J9 → fi` 工厂，不应调用 lab Canvas 那个刻意不支持的 `addNodes` 口。让 c7 的精确分支复用这套原 factory/原 addNodes→O8→r6 创建队列；只增一项输入专用、严格解析的“摘录来源”metadata，仿现上传元数据携带位置，不让客户端伪造 `lcos_ref`。原序列化是否完整携带这一项，必须先用真实 fi/M8/r6 执行证明，不能只看对象里有字段。
3. **同一现有 backend producer 增来源步骤。** [node-lifecycle.freshText](<E:/Codex 项目/LCOS夺舍计划_20261013/lab/pilot/node-lifecycle.ts:410>)已调用原 [createTextArtifact](<E:/Codex 项目/LCOS夺舍计划_20261013/lcos/apps/local-core/src/text-artifact-service.ts:125>)一次，并在原 composite transaction 内登记 Artifact/Revision/FileRecord/View、Workspace 与 nativeBinding。窄认输入来源字段后先核 project/artifact/revision/View/FileRecord、实际确版 bytes、locator 和 quote/content；非法时在创建前拒绝。保原普通 text、上传、duplicate/restore 白名单，不把来源字段泛放开给任意 data。
4. **接回同一持久来源。** 使用已验证 [encodeNativeMaterialSourceAnchor](<E:/Codex 项目/LCOS夺舍计划_20261013/lab/pilot/native-text-location-persistence.ts:16>) 与同一 validator，沿原 `reference` Relation + evidence 的 artifact/revision/sourceAnchor 写入。建议把旧 ingress 的“确认/复用关系证据”步骤抽成一个共享窄 owner，旧入口与新创建链都委托它；不复制整份旧 producer，更不同时调用旧 receive 和 freshText。sourceAnchor 继续是现 opaque 字段，无新 Core API/实体。两代摘录的来源分别指向各自直接父材料的准确版本。
5. **保原创建回执与撤销。** 结果进入现 `lcos_operation.kind=create`、原 client→实际 node id 回执与 [native-create-identity 回填](<E:/Codex 项目/LCOS夺舍计划_20261013/lab/startup-history-intent.js:1942>)。Undo/Redo 由原 [applyAction](<E:/Codex 项目/LCOS夺舍计划_20261013/lab/pilot/node-lifecycle.ts:845>) 的 delete/restore owner 处理：Redo 恢复原确切材料，不再创建第二份 Artifact，不把已保存父来源关系删掉。不要另写历史数组或为新创建套“所有历史都有该节点”的投影回填。

这条链的“新建文本”仍只有原 Core text producer 一个 owner；新增的是原手势与来源关系之间的桥，不是第二个生产者。

## 部分提交与恢复必须诚实

- 原 Core 文本 composite、原 Relation ChangeSet、原 Huabu 空间/历史是既有独立 owner，不能描述成一次跨系统原子事务。
- 已拿到 child 确切回执、随后来源关系或 native 显示失败：保这份 child/原操作，原 toast 给具名“材料已保存、来源/显示待核对”，沿原失败回执做 GET 核对；不得重跑 createTextArtifact。若确需补尚未确认的关系步骤，应先读取原关系/evidence，只补该步，不自动重建正文。
- 文本 POST 已发出但响应丢失、尚无 child id：现原 text producer 没有通用请求去重键，不能按标题/正文/时间猜“就是那一份”，也不能自动重发。先保原队列/操作的未知结果状态与现结果核对能力；这属于具体不确定提交场景，不能用“再拖一次”假装恢复好了。是否现 operation journal 足以读回，施工时必须执行断响应反例确认。
- 换项目/Canvas/API/Workspace、取消、未保存编辑和只读 owner 都保原保护；创建已提交后不把已知 receipt 发送到新页面。界面只说明用户结果，不把内部 DTO / sourceAnchor / API 错误暴露成操作按钮。
