# 非材料节点：原颜色入口与分层接线

日期：2026-10-27。范围：本批前端 ColorPin Provider、controller、原 Pin/More 工具条与原颜色组；导航 backend、Core/MCP、原 Canvas sync 由各自 owner 另档。本报告不把源级专项当真实页面完成。

## 结论

- 有真实领域身份的 Collection、Conversation、Run、ResultSlot、Note、Scope、Workspace 使用原 Core entity 颜色；材料继续使用所见的准确 View。
- 没有领域绑定的普通原节点使用原 `data.color_pins`，没有伪造 View/Run/Workflow。原六预设 palette 保留；接口设置的任意规范六位颜色可回显。
- custom 节点共用 TapNow 原 `ua → JT/Vde → Dg/Hie`，不是再画一套外壳。原节点正文、原标题/状态/查看动作不搬家。
- 同一种颜色只有一个原顶部组。Core membership 与普通空间节点分开保存、合并展示；managed 节点遗留 raw 影子不再重复计入。
- 普通组无 definition 的原命名缺口已在 2026-10-28 补源码：沿原 inline 改名只创建真实颜色定义/名称，0 membership/0 伪对象；已有同色真实 definition 继续沿原共享名称/CAS。源级验证和实际 GUI 验证分列，详见 `docs/普通颜色组独立命名_前端接线_20261028.md`。

原 `GET /api/canvas/v1/canvases/:id` 用于已保存普通节点核对；写只发 `POST /api/lcos/canvases/:id/gui` 的 `{type:'SET_COLOR_PIN',nodeId,color:'#RRGGBB',present:boolean}`。不发正文、位置或任意 data patch。原 Canvas sync/SSE 负责合入外部结果，没有本地 setter 伪造成功。

有效 ACK 后被 Agent 反改：显示“颜色标记刚有变化，已显示最新结果”，清本次已知 attempt，不重放。无 ACK/坏 ACK 且结果仍不明：保留未知与显式核对，原错误不清。只有实际记录改变才清旧成功文案，几何变化不会清。

补齐原窄 GUI route 的具体读失败边界：返回 `status:unknown` 但带完整、准确且已保存的空间回执时，保留这个有效 ACK，再独立读取当前字段。后来被 Agent 反改会成为已知变化；`unknown` 没回执或坏回执仍不解除未知。没有用当前颜色相同去假造丢失的 ACK，也不重发。
