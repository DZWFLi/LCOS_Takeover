# Composer 原会话接入画布四工具 · 最小接线研究

后续实测修正：本文是施工前研究，当前结果见[原Composer真实接通记录](../Composer画布工具接入_20261023.md)。实际发现 context_usage 仅列模型可见工具、会排除 deferred；runtime-add 不会刷新已初始化模型的声明；过长服务名被供应商改写后丢失工具操作后缀。最终采用原 alwaysLoadTools、原 setTools 刷新和原 native UUID 短名称，未设 trust 或跳过原确认。Main/Context 真实查询、原确认、真实模型移动及原 Undo/Redo/刷新已通过。原同会话既有消息从8条保留扩展到24条；失败归档未删除。以下规划和“未接”结论按研究时点阅读。

日期：2026-10-23。范围：只读当前源码与实际供应商包；没有产品编辑、服务启停、MCP 挂载或模型调用。

## 结论

已有独立 HTTP／MCP 客户端成功，不等于原 Composer 已经拥有工具。当前原 Composer 发送仍没有把现场地址带到服务端，实际 ACP bootstrap 也没有四工具配置。

当前真实供应商 Qwen Code 0.26.0 已有原生 **session 级 runtime MCP add/remove**。最小做法是在现 facade 的原发送路径，校验当前会话与当前 Core Workspace，使用原 Host Bearer 调用一个固定自有 MCP 的窄方法，然后继续原 Core 发送。可以不改 Core 领域 contract，不更换 native session，不写共享供应商 settings，不改已安装 agentlet daemon。

这条路线依赖当前真实 Qwen 的供应商扩展；不能据此宣布其他 ACP 供应商已支持。方法不存在必须如实返回不可用。

## 不改领域 contract 的最小 patch

1. 在原发送调用捕获现有 UI 现场地址，通过两个 transport header 交给 facade，例如 `X-LCOS-Canvas-Id`、`X-LCOS-Workspace-Id`。它们只是待验证的地址提示，不是授权。`lab/server.mjs` 仅传这两个字段给 facade，不把它们转发给 Core；原发送 JSON 原样保留。
2. facade 识别上述唯一原 send 路由，验证 project、connected conversation、已绑定的 continuation operation 与原 canonical session。用 `resolveKernelCanvas` 验 canvas/workspace 的精确配对。再核对原 originMeta 和 Host 现存 owner 的 native、transport、thread、agentlet。任何不一致都在模型发送前失败。
3. 有实际 conversation projection binding 时检查它仍指向同 canonical 会话；右栏对话可能尚未放到画布，不能为获得工具而强迫新建一个节点。工作区地址不从所有 projection bindings 中猜唯一值，也不用 Referer／浏览器全局 activeCanvas。
4. facade 用已有 `HUABU_HOST_TOKEN` 调原 Host 的受限工具准备方法。Host 只接受会话身份和已配置的 canvas 枚举；Python 解释器、脚本、runtime label、服务名全部从服务端配置构造。拒绝调用方提供 command、args、env、URL、文件路径或其他 server name。
5. Host 在原 `AcpAgentClient` 上通过 SDK `extMethod` 调 Qwen 原 session runtime-add。确认实际回执后，facade 继续原 `coreProtocol.handle`；消息保留原 reservation、完整 Scope attach、原 prompt、归档与回执。
6. 不把新“已连接工具”结论持久化为第二事实。运行时准备回执只属于原 live client；断线后重新读原 owner 和供应商实际工具状态。

### 必须一起处理的两个具体竞态

- **准备与发送之间被切现场**：如果 A 先挂 Main，B 又挂 Context，A 才进入 prompt，A 会误用 Context。facade 按既有 exact live owner 在“准备工具＋整条原发送”期间串行，忙时拒绝而不排队重发；Host 窄方法同时拒绝原 client 已有 prompt 在执行的情况，await 后重新核 registry 和 connection。只给瞬间 runtime-add 加锁不够。
- **同 messageId 的已完成／未知重试**：先读原 Core turn／journal。complete 走原回执快路径；pending／unknown 继续核对，不先切工具再发送，也不把 MCP 重新连接变成原消息重放。UI 保留的原 send ticket 应一并保留该次 transport 地址；不要在重试时重取全局现场。

原 `AcpAgentClient.prompt:499` 已按 sessionId 拒绝第二个 in-flight prompt，但锁从实际 prompt 才开始，覆盖不到前置工具准备，所以这一空档需要在现调用路径中收拢。

同一 session、服务名及配置再次 add，供应商已有同连接分支返回 `replaced:false` 与实际 `toolCount`；切现场则以同一服务名替换为新 canvas args。不能每轮随机服务名导致残留多个旧现场工具。

## 生命周期

| 场景 | 处理 |
|---|---|
| 新聊 | 沿原创建与 Core bind；确认真实新 native identity 后，在第一条原 send 的具体现场挂四工具。不能给新聊借旧 native session |
| 已有健康续聊 | 在同一原 client／native session 上 runtime-add；不做 session/new/load，不换 conversationId |
| 真断线恢复 | 仍只恢复原 native；原 owner 确认后，按下一条原 send 的具体现场重新 ensure；不把上个进程的本地缓存当已挂载 |
| 同会话换现场 | 完成当前 turn 后，下条 send 用明确的新现场地址替换同一自有 server config；对话与原归档仍是同一个 |
| 正在生成时换现场 | 保留本轮捕获的原 canvas。不得热切该会话的 MCP 目标；新请求如忙则如实提示，不能排队后偷偷发送 |
| 无可验证现场 | 普通文本对话仍可保留；不能让上一现场写工具在未声明目标的发送中悄悄继续可用。进入工具路径时应要求原 UI 地址或明确移除自有服务，不猜 Main |
| 换项目／断开原 client | 不移植旧项目 MCP。只清理自己原 session 的 runtime server；不关闭其他会话或供应商原 MCP |

## 认证与配置隔离

- 原 Host token 与 facade kernel token 是两个进程各自的连接凭据。`start-linked-continuation.mjs:108` 只给 Core `HUABU_HOST_TOKEN`；没有把 Host 的 `HUABU_CONNECTION_TOKEN` 注入 facade。不能用 agentlet 的 `AGENTLET_TOKEN` 代替 facade kernel token。
- Python 继续从既有 `kernel-connection.json` 在每次请求时读取当前 facade 连接配置，拒绝非 loopback、代理、重定向；不把 token 写进 MCP args、供应商 settings、对话或报告。
- **现原 Host 控制路由认证缺口必须在新能力边界补上**：`app.ts:205–230` 在未配 Basic Auth 时只对 `/api/rfs/` 强制 Bearer，现 `/api/acp/continuation/*` 控制请求没有这项强制校验。新窄方法必须验证原 `getConnectionToken()`，不能只因为 HostTransport 带了 Bearer 就假定已验证。沿用原 token 即可，不引入新令牌体系。
- Qwen runtime-add 会剥离配置中的 `env、headers、trust、cwd、includeTools、excludeTools、oauth` 等字段，因此不能依赖这些字段做秘密隔离或静默授权。
- **已定位的子进程环境泄露面**：Qwen `createTransport` 将 `sanitizeChildEnv(process.env)` 交给 stdio MCP；该函数只删 Qwen 内部四类 secret，不删现 launcher 的 `OPENAI_API_KEY`。自有 MCP 入口需立即剔除不需要的 provider／Host／Core secret env，或经自有精简 launcher 以允许列表环境启动。无需读值或新存密钥。当前 Python 实现只读本地 kernel 文件，不需要模型 key。
- 此 MVP 仅接预配置、固定的四工具 MCP；不接受页面添加任意第三方服务，亦不开放任意 command 或 URL 执行。

## 实际验收要求与剩余边界

1. 先无模型：在原已有 native 会话挂工具，读回同 session 的四工具；再 remove/add 验证，不创建新对话、不改变原消息数。
2. 用原 Composer 真发送一次“读取当前画布”任务，确认模型实际调用原 MCP 工具，而不是仅回复自己已经知道。核对 original native／thread／transport 和 Core 新消息归档。
3. 原 Composer 连续混合 Scope 两次发送仍全量带集合、附注、对话、Run；工具上下文与 Scope 内容附件是不同东西，不能拿 workspace 引用充当工具授权。
4. 同会话 Main→Context→返回，工具实际只读目标现场；同时另一会话仍留原现场，不能用 workspace 级状态冒充 session 隔离。
5. 断线恢复后仍为同 native，会话工具重新读回可用，然后连续发送。工具连接未知不自动重发模型或写操作。
6. 一个真实位置写入须核对原 Core／Huabu receipt、TapNow SSE、原 O8 Undo／Redo，以及正在拖动／编辑时保护。缺任一链不算模型写工具闭环。

**权限尚需单独实测**：`continuation-prompt.ts:149` 对无 Run 相关输入 owner 的续聊 permission 目前统一 cancel；Host 只有 runCorrelation 才转给原 Core input。MCP runtime-add 又不接受 trust。模型读工具或许不触发确认，但模型 `set_node_geometry` 可能被原保护拒绝。不能为了绕过它新造一个 Run，不能笼统 auto-allow，也不能删除保护。若需确认，沿原会话／原输入归属补桥；尚未接通就继续留账。
