# 上下文工作区与三现场接入 TapNow 评估

## 结论

后续补充：用户要求避免硬塞后，已核对“原 TapNow 多画布协议 → 本地兼容层 → Core + Huabu 无头空间服务”的备选路线。它不依赖整体移植 LCOS 组件树，见 [协议翻译与无头空间承接方案](./协议翻译与无头空间承接方案_20261013.md)。下文的高难度指原整包里硬塞整套宿主，不能用它代替新路线的分阶段评估。

用户已确认三视图指 Main / Context / Workflow 三现场。

能接，但这已经是项目级集成，不是给文字节点加几个按钮。保留现有 LCOS 三现场、Core 和唯一 Huabu 空间引擎，采用 TapNow 的节点/工具视觉，整体中等偏上；要求原 TapNow 整包与其画布运行时原样保留，再硬塞现有 Context / Workflow，则难度高。

两者不是同一种工作量。当前真实实验验证的是前一种路线里的局部节点采用：原 Huabu 作宿主、TapNow leaf 作呈现，并非完整 TapNow 壳已经采用。不存在“整套 UI 无改动、只换服务器地址就得到三现场”的证据。

## 现有三现场已有哪些基础

- 路由组合根 LcosProjectShell 已按 Main / Context / Workflow 挂载工作现场，不需从头发明三场景系统。
- 三现场共享同一个 Project 和材料身份，各现场由 Core Workspace 提供 canvasId，保留各自布局、视口和空间历史；这不是三份项目或三套 Core。
- LcosWorksiteStage / CanvasHostBoundary 复用唯一 Huabu Canvas 运行内核，绑定身份读好才开放受管节点编辑，不另造第二 ReactFlow/store/camera。
- useLcosWorksiteNav 通过实际 switchCanvas 成功后才更改现场与 URL，失败保持原现场。
- 原 switchCanvas 会先 drainPendingSaves；版本冲突、仍在保存或内容队列未清时拒绝切换。不能换成单纯切三个 DOM 页签并丢掉这些行为。

## 上下文不是一个空面板

当前复制 Gen2 源码中的 ContextWorksite 已挂载实际画布、Context Atlas 和子现场导航。Atlas 沿 Core Assembly/Warehouse 读上下文对象，支持搜索、分页和状态反馈，并根据明确 Workspace 映射进入目标。Context 子现场挂 TemporalRail，读取真实 temporal index，提供历史分组定位和预览。

这些现成组件和数据客户端可复用，但完整工作区不只有卡面：项目/Workspace 身份、上下文成员语义、材料引用、来源 Reader、跨现场投放、返回来源、历史定位等都要接到真实 caller。

需要保留的真实缺口：

- Context 卡面成员摘要不等于成员编辑已接通。canonical Collection 的成员读取/移除另有路径，不能直接算成 Context 的同一能力。
- TemporalRail 是时间事实定位和预览，不等于上下文分支/演进编辑。
- Atlas 自身的创建集合入口只在 Main 的 main-collections 模式出现，不能据此证明 Context 全套创建/编辑已完成；其他入口需要另按源码核对。
- 若用户要 Gen1 已有、当前 Gen2 尚未承接的上下文功能，这部分仍是业务能力承接，不会因为换成 TapNow 外观自动补齐。

## 难度分层

| 目标 | 判断 | 工程内容 |
| --- | --- | --- |
| 复用上下文卡面、目录和读取展示 | 中等 | 视觉容器、Core client 配置、真实对象映射、焦点/窗口宿主 |
| 沿现有三现场壳采用 TapNow 外观，保留真实保存/切换 | 中等偏上 | 三个 root Workspace、原 Canvas 切换、binding-aware renderer、状态隔离与恢复 |
| 完整 Context/Workflow 动作与跨现场流转 | 中等偏上至高，取决于缺口 | 材料引用/装配、子现场、时间定位、Composer/Run/Review、未承接业务 |
| 原 TapNow 编译整包及其画布不动，注入上述整套系统 | 高 | 原整包挂载点、跨 runtime 事件/React、唯一空间 owner 选择、协议与业务接线 |

UI 能显示只解决其中一部分。完整度和稳定性仍需逐动作测量，不把已有源码当成 TapNow 接入已完成。

## 最重要的三处接口

1. **工作现场地址。** Core Project / Workspace / canvasId 与 URL/导航对应准确，不能靠标题或数组第一项猜目标。
2. **对象身份与动作。** 同一材料跨现场显示应保留 Artifact / Revision，不把引用误当文件复制；跨现场移动/投放沿既有语义入口。TapNow node.id 不能直接替代材料身份。
3. **空间与输入生命周期。** 一处空间 owner 负责坐标、选择、resize、连线、视口和 undo。编辑未保存时切现场、拖到 Context 接收区、从子现场返回都要接原行为，避免两个 runtime 同时改位置/相机。

这些是现有接缝的组合和验证，不意味着要重新开发云后台。

## 当前实验与下一条验证

17879 pilot 已验证真实临时 Core + 原 Huabu + 原 TapNow 图片/文本 leaf，单个 canvas、两个合成节点；之前 Core 6 项、Huabu 4 项、浏览器 6 项验证通过。当前 Core 代理只承接 GET / PUT；它尚未承载完整 Context/Workflow 创建、装配和执行动作，不能把节点测试外推到三现场。

下一条最有信息量的验证是：在同一新合成 Project 的三个真实 root Workspace 中切换，同一材料以各自 View 呈现，逐现场拖动/编辑/保存/刷新，再验证一次真实 Context 引用或投放。只有这个闭环回来，才能说三现场主体已接通。

这是推荐的后续验证范围，本轮没有自动实施，也没有创建 Workspace、修改用户材料或提交模型任务。
