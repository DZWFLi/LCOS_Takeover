## 实际原回执

原 client：[colorPins.ts](../lcos/apps/web-gen2/src/backend/colorPins.ts)。改名方法由 [原 client 窄变换](../lab/native-core-color-pin-transform.mjs) 接入。

| 操作 | 最小有效证据 | 不能误用 |
|---|---|---|
| assign | flatten `{definition,membership,changeSetId?}`。准确 definition ID/project/规范颜色；membership ID/project、colorPinId 等于 definition.id、targetRef 等于捕获目标，原日期字段存在。 | 不能把“Promise 返回了任何对象”当 ACK；成员错目标不算 ACK。 |
| remove | `{deleted:true,membershipId:本次准确ID,changeSetId?}`。准确原 HTTP404 也证明请求已完成，可读回当前状态。 | 不追删后来新建的 membership ID；同 ID 被原 Undo 恢复时提示已变化。 |
| rename | `{definition,changeSetId?}`。准确 definition ID/project/color/createdAt，label 等于请求的裁切后名称，updatedAt 存在。 | 不要求 ChangeSet 必须存在：原 no-op 合法没有新 ChangeSet。后续不同名称不是“旧请求还没结束”。 |

Core 原 assign 会对同 definition+target 返回 existing；原 rename 本名也可返回 no-op。两个真实无 ChangeSet 回执均单独验证，不能把它们当无 ACK。

## 已验证的流程

- 有效 assign ACK 后成员被删、同目标同颜色被新 ID 替换：采用真实当前状态，needsCheck=false。
- 有效 assign ACK 后 GET 失败：保留 ACK；后来记录被删，原 verify 只 GET 即可结束等待，不补发 assign。
- assign 没收到回执，或回执 target 错误且当前记录缺失：仍 unknown，重复点击不追加写。只有真实后来出现的准确 canonical 成员才能满足原验证条件。
- remove ACK 后新 ID 出现：旧请求只完成旧 ID 的删除，新成员保留；GET 失败再 verify 也不追删新 ID。
- 实际原 Core DELETE404 后，原 ChangeSet Undo 恢复同 ID：当前颜色重新显示，原请求结束，不永久 pending、不再删除。
- rename ACK 后被更新的 CAS 名称覆盖：采用后来的名称，不把前一个名称写回。
- rename ACK 后 GET 失败，恢复时已是另一个新名称：verify 可结束已知请求并显示新名。
- rename 没收到回执，当前为另一个名称：仍 unknown，不自动重放；后续准确请求名称出现才满足原验证。

测试执行实际 `createNativeColorPinController`、实际 `CoreColorPinClient/HttpClient`、原 Core 路由/SQLite/MutationSafety/ChangeSet；仅在确切回执前后插入受控外部原操作或丢响应。没有替换 toggle/verify 算法，没有用 setter 清 pending。
