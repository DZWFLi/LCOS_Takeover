# REA 对 TapNow 夺舍计划的适用性评估

日期：2026-10-13（Asia/Shanghai）。工作区：LCOS-DSH-03。

实测更新：用户已授权并完成静态对照。预加载依赖展开有增量，但当前 IPC 配对、HTML 内联与 Canvas 语义覆盖不如资料预期；本文件保留调研判断，执行结果以 [REA 静态对照实测](<E:/Codex 项目/LCOS夺舍计划_20261013/docs/REA静态对照实测_20261013.md>) 为准。

## 结论

有帮助，值得做一次小范围试验。它适合充当逆向索引器：帮我们定位组件依赖、状态与请求流、Electron 桥接边界；不应把它当成“一键恢复原 TSX 工程”的工具。

查到的项目是 [morluto/rea：Reverse Engineer Anything](https://github.com/morluto/rea)。本轮核对官方文档、发布记录及实现线索，没有安装、运行、克隆 REA，没有注册 MCP，也没有启动 TapNow 或连接其云端。

## 为什么对我们有用

REA 的 JavaScript 路线能直接静态读取目录或 ASAR，不执行目标代码，也不要求 Hopper/Ghidra。它记录模块/import、入口、端点、preload/contextBridge 和 IPC。与我们手中的编译 JS、桌面壳副本相匹配。[6.4.0 静态分析说明](https://github.com/morluto/rea/blob/rea-agents-6.4.0/docs/javascript-artifact-reconstruction.md)

| 我们要解决的问题 | REA 能提供的线索 | 对夺舍计划的增量价值（判断） |
| --- | --- | --- |
| 原 Canvas 组件能否单独取出 | 词法定义/读取、闭包、可静态解析的调用和参数/返回流 | 从“这个 chunk 导入谁”继续追到“这个函数具体依赖什么” |
| 哪些状态、请求还连着云端 | 属性、端点、请求构造与响应消费者的静态关系 | 帮我们定位自己的 adapter 应放在哪一层 |
| 去掉 Electron 会损失什么 | renderer → preload API → IPC → main handler 的关联 | 复核已分类的 77 个 IPC，找浏览器替代与 LCOS bridge 的接缝 |
| 早期网页包与安装版哪些功能相近 | 版本比较、结构与导出返回形状比较 | 辅助挑选更容易回收的旧模块；相似不等于运行等价 |

这些追踪/比较能力有发布版工作流，不只是 README 的愿景。动态调用、动态属性或不唯一的目标仍可能是 unknown；静态可达不证明实际执行。[6.4.0 追踪与比较说明](https://github.com/morluto/rea/blob/rea-agents-6.4.0/docs/javascript-application-workflows.md)

发布版实现也确实按 AST 扫描 ESM import/export、动态 import、端点和 Electron 调用，不是纯关键词搜索。[静态分析实现](https://github.com/morluto/rea/blob/rea-agents-6.4.0/src/domain/javascript/javascriptStaticAnalysis.ts)

## 它不会替我们完成什么

- 不会凭空找回已丢失的类型、注释、原目录和业务命名，也不能从客户端拿回没有打包进去的云端实现。
- 不会自动把 React 编译调用整理成我们的可维护组件工程。提取、重新命名、设计接口、个性化修改和回归仍是工程工作。
- Webpack/Rspack 模块工厂恢复不能直接等同于恢复 TapNow 的原始组件边界。我们当前主要面对 ESM chunks 和庞大的共享入口。
- 24 个独立工具的逻辑大量内嵌于 HTML；目前不能仅凭“支持 HTML script entrypoints”认定内嵌脚本也被完整语义分析。这个覆盖需要实测确认。

它另有 recover_javascript_sources 路线，但依赖用户另行提供 Wakaru，并非 REA 自带恢复引擎。6.4.0 的这个适配器只声明 Linux x64；不算我们当前 Windows 上开箱即用的能力。它能派生可读模块，但结构提取可能退回单文件，官方 scope-hoisted 夹具就没有拆出多个模块；原命名与运行等价仍不保证。因此可以作为后续专项候选，不能据此承诺把 13 MB 共享入口自动变回组件工程。[发布版源码恢复说明](https://github.com/morluto/rea/blob/rea-agents-6.4.0/docs/javascript-recovery.md)

以上是针对当前材料的工程判断。已有 [拆分与反编译实测记录](<E:/Codex 项目/LCOS夺舍计划_20261013/docs/拆分与反编译评估_20261013.md>) 已证明：493 个 JS、1,139 条字面导入边可扫描；13.14 MB 主包可解析和格式化；原组件挂载点也已经能换成我们的可编辑面板。REA 的价值应体现在更深入的关系定位，不是重复排版。

## 版本与成本：别把 main 当发布版

GitHub 当前最新发布记录是 6.4.0（2026-10-11）。建议试验明确使用该版本，不直接照 main 的所有新选项操作。[6.4.0 发布记录](https://github.com/morluto/rea/releases/tag/rea-agents-6.4.0)

发布版声明 Node 22.x ≥22.19、24.x ≥24.11 或 26+；我们已有的 Node 22.22.3 满足要求。package 中有 Windows x64 支持。[6.4.0 package.json](https://github.com/morluto/rea/blob/rea-agents-6.4.0/package.json)

6.4.0 默认每源文件分析器 V8 old-space 1024 MiB、超时 300 秒；这不是实测耗时，也不是整个进程的内存上限。我们的主入口有约 244.76 万 AST 节点，深层语义分析能否完整覆盖还未验证，不能从 Babel 几秒解析外推 REA 的性能。超限结果应按 partial/unknown 解读。[发布版资源限制](https://github.com/morluto/rea/blob/rea-agents-6.4.0/docs/javascript-artifact-reconstruction.md#large-results)

main 文档已有 source_paths / --source-path 选择和更多语义容量设置，6.4.0 文档没有这些选项。本轮不把它们列为发布版可用能力。[main 的选择范围说明](https://github.com/morluto/rea/blob/main/docs/javascript-artifact-reconstruction.md#select-sources-before-analysis)

目前只能判断它有机会降低人工追线成本，不能承诺“节省一半时间”或给整包运行时间；我们尚未跑 REA 对照测量。

## 怎么试才有意义

建议下一步只做一次性 CLI 静态试验，不先执行 rea setup、不全局安装、不改当前 agent 配置。setup 会注册 MCP 并安装配套指引，属于另一项环境变更。[官方安装说明](https://github.com/morluto/rea/blob/rea-agents-6.4.0/docs/installation.md)

1. 先分析复制包的 resources/app.asar，复核已有桌面桥接分类。不要指向原安装目录。
2. 再分析 Web 副本，重点追 Canvas 页面、Agent host 共享导出和云端请求；若为缩小成本另取小目录，明确那只是选定材料，跨目录依赖可能缺失。
3. 看它是否找到我们尚未确认的函数级依赖、请求消费者或 IPC 路径；记录实际耗时、内存与 coverage，不只看报告多大。
4. 用现有离线浏览器操作验证拆分判断。成功追到代码不等于成功取出组件，更不等于删依赖后页面还能工作。

包未缓存时，npx 会联网下载工具；本地分析不等于整个 AI 协作链路不外传。若接 MCP，返回内容会进入模型上下文，报告里的端点参数和路径也可能敏感。试验输出应留在私有工作区，分享前筛掉凭据与用户数据。REA 的 MIT 许可只覆盖工具自身，不表示 TapNow 代码也变成 MIT。[REA 说明与许可入口](https://github.com/morluto/rea/tree/rea-agents-6.4.0)

本轮没有新增 hash、冻结 contract、baseline 或 gate，也没有改变既有安全措施。最终建议：把 REA 加为可选逆向辅助工具，主线继续是“定位 → 回收组件 → 接自己的数据 → 真实交互验证”，别让装工具变成新的开工门槛。
