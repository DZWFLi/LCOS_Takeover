# Core 实时对话归档修复

已接好原归档生产链，隔离验证通过；这份记录不代表真实页面已验收。

## 原因与修改

原 Core bind 已创建 canonical Conversation，但 `source_path/source_content_hash/source_file_name` 为空；原 append 只写规范化消息。因此完整 Scope 正确地拒绝把入口或消息投影当作已确认原来源。

现沿同一个 `ConversationImportService` 的 `reconcileContinuationArchive` 补齐来源。仅处理有唯一原连接、完整 continuation identity、且不是原导入 Artifact/View 的 Core 实时会话。手动导入和供应商原文件不重建。

触发位置沿用原链：bind 确认后、原 collaboration-send 前与 append 后、原归档 inspect，以及原 sections/refresh 维护动作。混合 Scope 的原 identity read port 先由原服务完成归档核对，再捕获稳定的 session/hash。原 walk、源 hash、media、附件版本与字数保护保留。

## 归档范围

- JSONL 明确标识 `producer: lcos-core-realtime`。
- 保留 Core 已保存的完整原消息，包括 id、seq、sourceEventId、正文、事件状态、toolCall、fileRefs、parentId 和原内容 hash。
- 每条消息保留原 operation/promptReceipt 中的 ordered/explicit 引用、完整 contextResolution、attach/send 回执来源；不从预览或标题拼内容。
- 当前 pending user 按真实 pending 事件归档，不造 assistant。原明确失败后释放的 reservation 保留为 Core 释放事件及原失败回执。
- **这是 Core 实时记录完整归档，不承诺供应商内部全部未回传的事件流。** 当前原 transport 只回传助手正文；未回传的工具内部过程不冒充已取到。
- 会话正文仍沿原消息/明确历史附件读取规则，不把过去整份 Scope 再递归塞进当前会话正文，避免自包含膨胀。

## 一致性与恢复

1. 已有来源先沿原 inspection 验证文件和原 hash，再校验消息、身份及冻结上下文来源。文件损坏、缺失或正文冲突直接失败，不从规范化表重写掩盖。
2. 新快照在原 `.creative-os/conversations/<session>` 内独占创建，写全并 sync、读回，使用原 SHA-256 和原 source 字段；不引入新 hash 规则。
3. 原 Importer SQLite 事务内复读同 session、消息和 journal，执行原来源指针 CAS，再提交。旧文件不原位覆盖，旧有效来源仍可核对。
4. 文件失败、事务异常或并发消息变化均保留旧指针；只清理本次未提交候选。同服务重试，不新建 session，不再次发模型。
5. bind 后本地归档失败保留已确认 identity，暴露错误供原操作修复，不把已确认身份误降为 provider 失败。
6. completed messageId 重试直接返回原 turn，不重读已经变化的自包含 Scope，也不重新 attach/send。pending/unknown 重试只保留并核对原记录。
